# 교훈 기록 (compound-engineering 기준 차용)

> 원본은 EveryInc/compound-engineering-plugin 의 `ce-compound` 와 `schema.yaml` 이다. 저장소는 `docs/solutions/` 대신 `.claude/lessons/BANK.md` 와 목적지 rule·skill 이다.

## 1. 남길 가치가 있나 — 세 조건 모두

1. **명백하지 않다** — 최종 코드·테스트·주석·기존 문서만 읽어서는 알 수 없다.
2. **오래 간다** — 이번 diff 를 넘어 유효한 불변식·제약·근본 원인·기각한 방법·결정이다.
3. **중요하다** — 잊으면 같은 실수가 재발하거나, 운영 사고(배포·예산·알림 폭주)가 나거나, 조사를 크게 다시 해야 한다.

반사실 질문으로 확인한다. **"이 교훈이 사라지면, 최종 코드를 읽은 다음 사람이 같은 실수를 하거나 같은 조사를 다시 할 가능성이 높은가?"** 아니면 남기지 않는다.

- "됐다", "고쳐졌다" 는 판단할 **시점**일 뿐 남길 **이유**가 아니다. 수고·diff 크기도 이유가 아니다.
- 진행 중이거나 검증되지 않은 해법은 남기지 않는다.
- 한 번에 교훈 하나. 여러 개면 하나씩 따로 판단한다.
- Codex 리뷰 지적은 **같은 종류가 두 번째로 나왔을 때** 교훈 후보다. 한 번이면 커밋 메시지로 충분하다.

## 2. 가장 좁은 집에 둔다

| 지식의 성격 | 둘 곳 |
|---|---|
| 기계로 강제할 수 있는 동작 | 테스트·assert, 또는 `.claude/hooks/guard.py` |
| 한 곳에만 해당하는 이유 | 코드 주석 |
| 이번 변경의 경위 | 커밋 메시지 |
| 결정·기각한 대안·진행 상태 | 옵시디언 `기술파악 - 결정 기록`·기능 노트 |
| 사용자 선호·일회성 사실 | auto memory |
| 수치·흐름·스키마 | `docs/pipeline.md`·`docs/database.md`·`docs/architecture.md` |
| 여러 파일·작업에 걸친 이유 | **BANK** → 두 번째 관찰 시 rule·skill 로 승격 |

BANK 는 맨 아래 칸일 때만 쓴다. 위 칸으로 충분하면 그쪽에 두고 끝낸다.

## 3. 겹침 판정 — 다섯 기준

기존 BANK 행과 목적지 rule·skill 을 grep 해서 **증상 · 근본 원인 · 해법 · 관련 파일 · 예방 규칙** 다섯 가지를 비교한다.

| 겹침 | 처리 |
|---|---|
| 4~5개 | 새 행을 만들지 않는다. 기존 행(또는 목적지 파일 문장)을 갱신한다. 이미 BANK 에 있던 행이면 **두 번째 관찰**이므로 승격한다 |
| 2~3개 | 새 행을 만들고 목적지 칸에 `통합 후보: <기존 행 증상>` 을 붙인다 |
| 0~1개 | 새 행 |

**관찰 수는 독립된 사건으로 센다**(REUSE — 같은 사례로 만들고 같은 사례로 확인하면 가짜 개선이 승격된다).

- 서로 다른 작업(다른 날의 다른 과제·기능)에서 각각 드러난 것만 한 번씩 센다.
- 같은 작업 안의 리뷰 반영 루프는 한 번이다. 같은 사건이 일일 노트·기능 노트·커밋·세션 기록에 각각 남은 것도 한 번이다.
- 반복 절차는 그 순서를 밟은 작업 수로 센다.
- BANK 행의 날짜 칸에는 관찰한 사건의 날짜를 모두 적는다(예: `09-10, 10-01`).

## 4. 트랙과 행 형식

- **버그 트랙** — 무엇이 깨졌고 왜, 어떻게 고쳤나. 증상 · 안 된 방법 · 교훈(원인과 해법) · 예방을 채운다.
- **지식 트랙** — 여기서는 이렇게 한다, 그 이유. 맥락 · 지침 · 적용 조건을 채운다. 안 된 방법은 비울 수 있다.
- **안 된 방법** 은 조사에서 가장 비쌌던 부분이라 가장 먼저 사라진다. 버그 트랙이면 반드시 적는다.
- **폐기 조건** 은 교훈이 레포 밖의 무엇(외부 API 동작·무료 등급 한도·라이브러리 버전·Gas Town·플러그인)에 기댈 때만 적는다. 무엇이 바뀌면 폐기인지와 **레포를 바꾸지 않고** 확인하는 법을 함께 쓴다. 레포 안 수정으로 풀리는 것은 폐기 조건이 아니다.

행은 표 맨 위에 추가한다.

```
| 날짜 | 트랙 | 증상 | 교훈 | 안 된 방법 | 확인 방법 | 목적지 | 폐기 조건 |
```

## 5. 기록 전 근거 확인

적는 문장에 파일 경로·함수명·커밋 해시·설정 키·로그 이벤트명이 있으면 지금 레포에서 grep 해 실제로 있는지 본다. 없는 이름을 적은 교훈은 다음 세션을 오도한다.

## 6. 정리 (월 1회 또는 BANK 가 20행을 넘을 때)

1. **폐기 조건 확인** — 조건이 적힌 행은 그 확인 방법대로 본다. 조건이 풀렸으면 지운다.
2. **승격** — **독립 사건 둘**로 관찰된 행은 현재 코드로 다시 확인하고 목적지 rule·skill 에 한두 문장으로 옮긴 뒤 행을 지운다. 문장에 사건 날짜를 괄호로 남긴다. 목적지 규칙 파일이 60줄을 넘으면 절을 나누거나 새 규칙 파일로 뺀다. 같은 내용을 코드 주석·테스트·훅이 이미 지키면 규칙에 옮기지 않는다.
3. **승격 뒤 효과 확인** — 지난 정리 뒤 승격한 규칙마다, 그 뒤 같은 종류 사고가 다시 났는지 일일 노트·커밋에서 본다. 다시 났으면 문장이 약한 것이니 고치거나 가드·테스트로 옮긴다.
4. **통합** — `통합 후보` 표시가 붙은 행끼리 합친다.
5. **낡음** — 90일 넘게 재관찰 없는 행은 지운다. 코드가 바뀌어 틀린 내용이 된 행은 고치거나 지운다.
6. 정리 결과는 옵시디언 일일 노트에 한 줄로 남긴다.
